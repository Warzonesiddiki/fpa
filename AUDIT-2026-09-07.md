## 2. Fixed this session (commits `3d60a75`, `deabb80`)

### 2.1 S-031 — broken build from incomplete extraction

`MappingWorkspace` was extracted from `MappingWizardPage` in PR #40 but kept
using `kind` (mapping targets + post-save navigation) while the store
subscription stayed in the parent. Moved the subscription into the workspace.

### 2.2 S-045 — headcount import was dead on arrival (real runtime bug)

`importDriverData(path, mapping, "")` hardcoded an empty `scenario_id`.
`DriverImportArgs` requires a `Uuid` and the native handler runs
`check_scenario_unlocked` — the import could never succeed outside the mock.
Wired a real scenario selector mirroring S-030's `DriverImportPanel`: select
with locked-marker, gated submit, i18n keys, and a page test that asserts the
gate + the 3-arg call. Also found + fixed a **second `<ImportPanel>` call
site** (empty-state branch) that the first patch pass missed — both now
consistent.

### 2.3 driver.import test contract (5 stale tests)

PR #40 added `scenario_id` to the pipeline but updated tests only halfway
(calls were updated, assertions were not). Aligned: `schema.test.ts` (valid
payload + empty-scenario rejection), `drivers.test.ts`, `headcount.test.ts`
payload assertions. Two latent bugs surfaced and fixed while doing it:

- `schema.test.ts` asserted `DriverImportData.safeParse({batch_id})` → `true`
  — impossible: `rows/audit_id/source_hash` are required. Never caught before

- S-030 test still asserted the pre-M2-5b copy ("driver data … unavailable")
  and disabled driver tab. Rewritten: driver tab is real and enabled; only
  Dimension master stays gated (matches the already-updated `destinationGate`

### P2 — Scenario dropdowns are only populated if S-050 was visited first

Both S-030's `DriverImportPanel` and S-045's new selector subscribe to
`useScenarioStore` but nothing triggers `load()` on those screens — on a fresh
app start the dropdowns are empty until the user opens S-050. Fix: guarded
load-on-mount in both panels (or a shell-level loader). Deliberately not done
in this pass to keep the main-repair patch surgical; tests that assert bridge
call sequences will need updating with it.

### P2 — PR #38 open and unreviewed ("feat: add fpa ECC bundle", `ecc-tools/fpa-1788689449051`)

Unknown content waiting on main. Given PR #40 merged unverified, review it
against the gates before merging; do not repeat the pattern.

### P3 — CSS bridge lags `tokens.ts` by 6 tokens

`tokens.ts` defines `primaryActive`, `primaryMuted`, `bgOverlay`,
`borderStrong`, `textDisabled`, `focusRing` — none are bridged as
`--color-*` in `index.css`. Harmless until a component references them via
`var()` (then they'd silently no-op, exactly like §2.5). Bridge them or add a
test asserting parity between `tokens.ts` and `index.css`.

### P3 — Warm warning-container token (design decision)

S-032's warning banner now renders on `onesurfacealt` (neutral). If the warm
tint matters, define `--color-onewarningcontainer` in DESIGN-SYSTEM §1.2 +
`tokens.ts` + bridge, then swap the one use.

### P3 — No automated gate caught the broken merge

CI exists but main absorbed a red PR anyway (merged before CI ran, or checks
ignored). Branch protection requiring the CI checks on `main` is still not
enabled — it was listed as an owner action in the 2026-09-06 status and
remains the cheapest insurance this repo can buy. Consider also a
`gitmoji`-free pre-push hook (`npm run lint && npm run typecheck`) for humans.

### P3 — Token-parity + undefined-reference test (proposed)

§2.5 was found by a one-off script. Institutionalize it:
`scripts/token-check.mjs` — parse `index.css` definitions, parse all
`--color-*` references in `src/`, fail on any reference without a definition,
fail on `tokens.ts`↔bridge drift. Wire into `npm run check`. (~40 lines; the
audit's script is in git history of this commit range.)
